**Rule ID:** LOG-003

**Description:** Log records do not contain sensitive data such as PII, financial identifiers, credentials, or health information.

**Rationale:** Telemetry data is typically stored in observability backends with broader access than production databases. When log records contain sensitive data, it creates compliance risks (GDPR, HIPAA, PCI-DSS) and security vulnerabilities. Application logs frequently dump user context, request payloads, or error messages that include credentials, PII, or other sensitive fields. This is especially common when using structured logging frameworks that automatically serialize request or user objects. OpenTelemetry Semantic Conventions [explicitly discourage](https://opentelemetry.io/docs/specs/semconv/general/attributes/#sensitive-information) recording sensitive information in telemetry.

**Target:** Log

**Criteria:** Log record data MUST NOT contain sensitive data. Common formats include:

- Email addresses (e.g., `user@example.com`)
- Credit card numbers (13-19 digits, after removing spaces and hyphens, that pass Luhn validation)
- Social security numbers or national ID numbers (e.g., `123-45-6789`)
- User identifiers that can be tied back to a person, such as `enduser.id`, even when opaque or pseudonymous
- Bearer tokens, API keys, or other credentials (e.g., `Bearer eyJ...`, `sk-...`, `AKIA...`)
- Passwords or secrets in key-value patterns (e.g., `password=...`, `secret=...`, `token=...`)
- Financial identifiers such as bank account numbers or tax IDs
- Health data in key-value patterns (e.g., `diagnosis=...`, `patient_id=...`, `insurance_id=...`)

The formats above are examples, not an exhaustive list, and this rule intentionally does not prescribe regular expressions. Detecting only the listed formats is not sufficient to pass: sensitive data in any other format, including formats introduced after this rule was written (such as the alphanumeric Brazilian CNPJ), also violates this rule.

This rule applies to every string and integer value in log record data (integers are matched in their decimal form), including values nested in array or map values:

- Log record bodies
- Log record attributes
- Log record event names
- Instrumentation scope names, versions, and attributes

Keys are evaluated together with their values: a non-empty value under a key naming a sensitive field, such as `password`, `secret`, `token`, `api_key`, or `ssn`, matches regardless of its format.

**Examples:**

- "Log record body contains `Failed login for user alice@example.com from 10.0.0.1`, which includes an email address."
- "Log record body contains `Payment processed for card 4111-1111-1111-1111`, which matches a credit card number pattern."
- "Log record body contains `Authorization: Bearer eyJhbGciOiJIUzI1NiIs...`, which includes an authentication token."
- "Log record body contains `{"user": {"ssn": "123-45-6789", "name": "Alice"}}`, which includes a social security number."
- "Log record attribute `user.email` contains value `alice@example.com`, which includes an email address."
- "Log record body contains `{"password": "correct-horse"}`, which includes a password in a key-value pair."

**Impact:** Critical
